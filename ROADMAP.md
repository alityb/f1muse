## Phase 2 — Validation pipeline
Every translated program passes an explicit gate pipeline before it could ever be execution-eligible; each gate rejects with a typed error that flows into the durable log and metrics taxonomy. Gates: (1) participation — entities must appear in `season_entrant_driver` for the scoped season; (2) coverage matrix — sources, fields, and operators outside supported coverage are rejected; (3) AST complexity budget — configurable limits on node count/depth, enforced pre-generation; (4) DB statement timeout — configurable, enforced in a read-only transaction, proven by a slow-query test; (5) typed signatures — per-source field/operator signatures enforced with field-level errors; (6) definitions/version check with a refresh path. Done when: every gate has pass and fail fixtures, all rejections are typed end-to-end, all wrapped suites are green, and PROGRESS.md is updated.

## Phase 3 — Core IR refactor
Snapshot current translator/lowering output for the full macro corpus as golden files first. Define generic core nodes — Source, Filter, Aggregate, Sort, Limit, Join, Compare, Delta — and re-express existing macros through them; `pace_delta` and classification remain thin surface macros that lower into core IR with no bespoke SQL paths. Type-check the IR against the Phase 2 signatures. Done when snapshots match (or every diff is intentional and documented) and all prior tests stay green.

## Phase 4 — Data coverage expansion
For each area: typed source/field definitions, extended coverage and participation gates, lowering support, tests, and golden examples. Areas: (1) qualifying classification as a first-class source; (2) event metadata / session scope with a well-defined default; (3) driver/team/event filters composing through core Filter nodes; (4) retirement-reason sampling — read-only, rate-limited, flag-gated script against production (PARTIAL with staging/fixtures if no access) plus a normalization map to a canonical enum with an explicit `unknown` bucket, tested against sampled fixtures.

## Phase 5 — Regression backbone
(1) 100-question golden corpus as data files (question → expected program, expected results where runnable on fixtures), covering all Phase 4 areas, edge cases, and deliberate expected rejections, with a runner asserting matches. (2) Property-based generators (`fast-check`) producing valid core-IR programs within budget; assert validation passes, SQL generates, invariants hold. (3) Metamorphic tests: vacuous filter is a no-op; sort inversion reverses order; `limit n` results are a prefix of `limit n+k`; commutative filter reordering is result-invariant. (4) Differential tests: SQL backend versus reference interpreter over fixtures, results must match. (5) CI wiring: golden + property + metamorphic + differential on every PR within a bounded time budget; nightly job runs extended generation, the production shadow smoke, and the 30-day report.
